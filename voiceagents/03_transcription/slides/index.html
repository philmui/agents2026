The one idea

Keep the line open, push audio, read text

You do not upload a finished recording.
You keep an open line and push audio the whole time.
Words come back the moment the server hears them.
mic → append →
transcription.completed

This is the simplest of the three capabilities: audio in, text out, no spoken reply. Learn it first, then add a voice.

The playing field

Six concepts, one CLI

Concept What it does When it matters
Transcription session session.type: "transcription" Text only, no spoken reply
gpt-realtime-whisper Realtime STT, billed per minute Not the file-based whisper-1
PCM16 @ 24 kHz The exact audio format Recording + declaring format
append Carries mic bytes in audio Every ~50 ms while you talk
Turn detection Decides when a phrase ends server_vad / semantic_vad / manual
completed Final text of your turn Printing the transcript

Audio goes in as append; text comes back as ...transcription.completed.

Concept 1 · One API, several modes

A transcription session is a one-way street

Set session.type to pick a mode.
"transcription": it listens, returns text, never talks back.
No response.create, no voice, no assistant turn.
SESSION_CONFIG = {
  "type": "session.update",
  "session": {
    "type": "transcription",   # listen-only
    "audio": {"input": {
      "format": {"type": "audio/pcm",
                 "rate": 24000},
      "transcription": {
        "model": "gpt-realtime-whisper"},
      "turn_detection": {"type": "server_vad"},
    }},
  },
}

Concept · The transport

Why a WebSocket, and why server-side

HTTP: ask once, one answer, line closes.
WebSocket: one line stays open, both sides send anytime.
Speech is a stream, so the shape must be a stream.

We run this on your laptop as a server because it holds your real API key in the Authorization header.

RULE Browsers never see the real key. Later modules hand the browser a short-lived ek_ token instead.

Concept 3 · What "voice audio" is

PCM16 @ 24 kHz mono, then base64

Sample: measure the sound wave many times/sec.
24 kHz: 24000 samples every second.
PCM16: each sample an int16 (−32768..32767).
base64: bytes wrapped as ASCII for JSON.
samples = np.array(
    [0, 15000, -15000],
    dtype="int16")          # PCM16
raw = samples.tobytes()     # bytes on wire
b64 = base64.b64encode(raw)\
        .decode("ascii")    # goes in "audio"

A stream of int16 numbers, 24000/sec, one channel. That is all "PCM16 @ 24 kHz mono" means.

Concept 4 · Pick the right model

gpt-realtime-whisper, not whisper-1

whisper-1
File-based. Upload a finished clip, get one transcript. Not live.
gpt-realtime-whisper
Realtime. Stream as you talk, text flows back. Billed by the audio minute.
CAUTION Realtime transcription is billed by audio minute, even during silence if the mic is open. Close the stream (Ctrl-C) when done. It is like a taxi meter.

Concept 5 · Capturing the mic

~50 ms chunks via a callback + queue

SAMPLE_RATE = 24000
FRAMES_PER_CHUNK = 1200  # ~50 ms

def mic_callback(indata, frames, t, status):
    # copy fast, send later
    audio_q.put(indata.copy().tobytes())

sd.InputStream(
    samplerate=SAMPLE_RATE, channels=1,
    dtype="int16",              # = PCM16
    blocksize=FRAMES_PER_CHUNK,
    callback=mic_callback)
24000 × 0.050 = 1200 samples
The audio thread must return fast, so it only copies samples into a queue. A sender thread does the slow base64 + send.
~50 ms: small enough to feel live, big enough to avoid spamming the socket.

Concept · Sending audio

input_audio_buffer.append

The server keeps a growing input audio buffer.
Each mic chunk is one append event.
event = {
  "type": "input_audio_buffer.append",
  "audio": base64.b64encode(chunk)
             .decode("ascii"),  # field: audio
}
ws.send(json.dumps(event))
CAUTION On the way in, bytes go in the audio field, not delta. delta is what the server streams back (partials now; assistant audio in response.output_audio.delta later). Sending "delta" here is wrong.

Concept 6 · Turn detection (VAD)

Three ways to end a turn, pick one

Mode Config value Ends a turn when
Server VAD {"type": "server_vad"} you go quiet (~200 ms)
Semantic VAD {"type": "semantic_vad", "eagerness": "medium"} your sentence sounds finished
Manual null (Python None) you send ...buffer.commit
CAUTION Only send input_audio_buffer.commit in manual mode. With server/semantic VAD on, manual commits fight the automatic detector.

Concept · Reading the transcript

completed (final) + delta (partial)

...transcription.delta
Partial words as recognized. New text in delta. Print in place.
...transcription.completed
Final text of the turn, in transcript.
if etype.endswith("transcription.delta"):
    sys.stdout.write(event["delta"])
    sys.stdout.flush()

elif etype.endswith(
        "transcription.completed"):
    print("YOU SAID:",
          event["transcript"].strip())
CAUTION These are input_audio_transcription.* (the user). Do not confuse them with response.output_audio_transcript.* (the assistant), which does not exist in a transcription session.

The GA gotcha

No beta header at general availability

OLD previews wanted OpenAI-Beta: realtime=v1
GA that header is gone; sending it can error
headers = [
  f"Authorization: Bearer {API_KEY}",
]  # that is the ONLY header you need
ws = websocket.create_connection(
    WS_URL, header=headers)
REMEMBER The format you declare must match the bytes you send. Open the mic at 24000 Hz int16 and declare {"type":"audio/pcm","rate":24000}. A mismatch garbles the transcript.
